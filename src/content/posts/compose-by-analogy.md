## 들어가며

나는 Java와 Spring Boot로 일하는 백엔드 개발자다. Android 화면을 코드로 그리는 도구인 Compose는 이번에 처음 써 봤다.

처음 보는 개념이 나올 때마다 Claude는 내가 익숙한 백엔드 개념에 빗대어 설명해 줬다. 그중 이해에 도움이 됐던 비유 네 가지를 적어 둔다. 하나는 글을 쓰며 다시 보니 어긋나서 더 맞는 비유로 바꿨다. 비유가 딱 들어맞지는 않아서, 다른 점도 같이 적었다.

## 1. 값이 바뀌면 다시 그린다: 템플릿 렌더링

숫자가 3 이상일 때만 "다음" 버튼이 켜지게 만들어 봤다.

```kotlin
BrandButton(text = "다음", onClick = { }, enabled = count >= 3)
```

`count >= 3`은 한 번 계산되고 끝나는 코드처럼 보인다. 그런데 +1을 눌러 숫자가 3이 되자 버튼이 저절로 켜졌다.

**비유.** Thymeleaf 같은 템플릿은 요청이 올 때마다 그때의 데이터로 화면을 다시 만든다. Compose도 비슷하다. `count`가 바뀌면 `count`를 읽는 함수를 처음부터 다시 실행하고, `count >= 3`도 새 값으로 다시 계산된다. 이걸 재구성(recomposition)이라고 부른다.

**다른 점.** 템플릿은 요청이 오면 페이지 전체를 다시 만든다. Compose는 요청이 아니라 값이 바뀌는 순간에, 그 값을 읽는 부분만 다시 그린다.

## 2. 다시 그려도 값을 잃지 않는다: @Cacheable

카운터를 처음 만들 때 `remember`가 빠져 있었다. 이대로면 +1을 눌러도 화면은 계속 0이다.

```kotlin
var count = mutableStateOf(0)   // 다시 그릴 때마다 0으로 새로 만들어진다
```

+1은 실제로 된다. 그런데 값이 바뀌어 화면을 다시 그리는 순간, 이 줄도 다시 실행되면서 0으로 새로 만들어진다. 1번의 "다시 그리기" 때문에 생기는 문제다.

**비유.** `remember`로 감싸면 처음 한 번만 만들고, 다시 그릴 때는 만들어 둔 값을 돌려준다. 같은 인자로 호출하면 메서드를 실행하지 않고 저장해 둔 결과를 돌려주는 `@Cacheable`과 닮았다.

```kotlin
var count by remember { mutableStateOf(0) }   // 처음 한 번만 만든다
```

**다른 점.** `@Cacheable`은 메서드 인자를 키로 쓴다. `remember`는 코드에서 **그 줄이 놓인 위치**를 키로 쓴다. 그리고 화면을 가로로 돌리면 이 값도 사라진다. 돌려도 남기려면 `rememberSaveable`을 따로 써야 했다.

## 3. 지정하지 않았는데 스타일이 바뀐다: MDC

가장 오래 헤맨 장면이다. 글자 크기 단계를 정하고 나니, 스타일을 준 적이 없는 버튼 글자 "+1"이 굵어졌다. 이유를 듣고도 감이 오지 않아 몇 번을 되물었다.

> 언제는 bodyLarge, 언제는 labelLarge. 규칙이 있어?

규칙은 "가장 가까운 바깥에서 넣어 둔 스타일을 쓴다"였다. 앱 전체에는 기본 스타일(`bodyLarge`)이 깔려 있고, 버튼은 자기 안쪽에 버튼용 스타일(`labelLarge`)을 다시 깔아 둔다.

> button에도 style 지정을 안 했는데 button의 labelLarge라고 해서 잘 모르겠어.

이 질문에서 막힌 지점이 드러났다. 나는 스타일을 지정한 적이 없는데, 누가 지정했다는 걸까.

**비유.** 로그에 쓰는 MDC를 떠올리면 된다.

```java
// 바깥(필터)에서 한 번 넣어 두면
MDC.put("requestId", id);

// 안쪽 어디서 로그를 찍든, 넘겨주지 않아도 requestId가 붙는다
log.info("주문 저장");
```

안쪽 코드는 `requestId`를 넘겨받은 적이 없지만, 바깥에서 넣어 둔 값이 알아서 붙는다. 안쪽에서 다시 넣으면 그 범위에서는 새 값이 쓰인다.

버튼도 같다. 버튼을 만든 쪽(Google)이 버튼 코드 안에 "이 안쪽은 `labelLarge`"를 미리 넣어 두었고, 내가 넘긴 `Text("+1")`은 그 안쪽에서 실행된다. 앱 전체에 깔린 `bodyLarge` 위에 버튼이 `labelLarge`를 덮어쓴 셈이다.

```kotlin
// Material 라이브러리 안의 Button (줄인 모양)
fun Button(content: ...) {
    ProvideTextStyle(MaterialTheme.typography.labelLarge) {   // 바깥에서 미리 넣어 둠
        content()   // 내가 넘긴 Text("+1")이 여기서 실행된다
    }
}
```

여기까지 듣고 나서야 정리가 됐다.

> 보통 스타일 지정할 때 button은 labelLarge임을 알고 labelLarge를 고치고, button인데 다른 스타일 지정하고 싶으면 그때 명시적으로 지정하니?

맞는 이해였다. 버튼 글자를 앱 전체에서 바꾸려면 `labelLarge` 하나를 고치고, 한 곳만 다르게 하고 싶으면 그 자리에서 직접 지정한다.

**다른 점.** MDC는 스레드를 따라간다. Compose의 스타일은 스레드가 아니라 화면 구조를 따라 안쪽으로 전해진다. 버튼 안에 있는 글자만 `labelLarge`를 받고, 버튼 밖의 글자는 앱 기본값을 받는다.

## 4. 주입받은 것을 버리지 않는다: 생성자 주입

화면을 그리는 함수는 크기나 여백 같은 꾸밈 정보(`modifier`)를 바깥에서 받는다. 받은 쪽에서는 소문자 `modifier`에 이어 붙여야 한다.

```kotlin
fun Counter(modifier: Modifier = Modifier) {
    Column(modifier = modifier.padding(horizontal = 24.dp))   // 받은 것에 이어 붙인다
}
```

바깥에서는 "상태바만큼 위를 띄워라"를 넣어서 넘겼다. 대문자 `Modifier`로 새로 시작하면 그게 사라져서, 숫자가 상태바 밑으로 들어가 버린다.

**비유.** 생성자로 주입받은 Bean을 쓰지 않고 그 자리에서 `new`로 새로 만드는 것과 같다. 바깥에서 설정해 넘긴 것이 사라진다.

**다른 점.** Bean은 한 덩어리지만 `modifier`는 꾸밈을 이어 붙인 목록이고, 적힌 순서대로 적용된다. 여백을 먼저 주고 배경을 칠하는 것과, 배경을 먼저 칠하고 여백을 주는 것은 결과가 다르다.

## 한눈에 보기

| Compose | 익숙한 것에 빗대면 | 다른 점 |
|---|---|---|
| 재구성 | 요청마다 템플릿을 다시 렌더링 | 요청이 아니라 값이 바뀔 때, 그 값을 읽는 부분만 |
| `remember` | `@Cacheable` | 키가 인자가 아니라 코드 위치. 화면을 돌리면 사라짐 |
| 안쪽으로 전해지는 스타일 | 로그의 MDC | 스레드가 아니라 화면 구조를 따라 전해짐 |
| `modifier` 인자 | 생성자로 주입받은 Bean | 순서가 있는 목록 |

## 돌아보며

비유 네 가지 모두 완벽하게 들어맞지는 않았다. 그래도 처음 보는 코드가 어떻게 돌아가는지 조금이나마 그려 볼 수 있어서, 이해하는 데 꽤 도움이 됐다.
